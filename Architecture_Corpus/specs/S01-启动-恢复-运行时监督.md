## Bootstrap Closure

### InstallationAnchor / BootstrapRuntime

OS service、shortcut、foreground launcher 与 Recovery CLI 必须先落到一个**不依赖当前 ProductGeneration** 的 installation-level entrypoint。Foundation 把它称为 `InstallationAnchor`。

```text
OS/service entry
→ InstallationAnchor
→ select verified BootstrapRuntime generation
→ Bootstrap Closure
→ select/load ProductGeneration
```

`InstallationAnchor` 只负责定位 installation root、读取最小 selector、选择 current/previous bootable BootstrapRuntime 并启动它；不得解析 normal Configuration、连接 normal Management API 或拥有 Subject/System Authority。

默认产品拓扑允许 BootstrapRuntime 作为稳定 Host shell 在同一 OS process 中加载选定 ProductGeneration 的 Host entrypoint；ProductGeneration 切换通过 maintenance restart 生效，不做正在运行 Host 的 in-place code swap。平台若采用独立 parent/child launcher，也必须保持相同 ownership/Recovery 语义。

BootstrapRuntime/anchor 的 exact executable/script/service-wrapper mechanics 属平台 L3 qualification；架构只要求**始终存在一个不依赖 replaceable ProductGeneration 的可启动入口**，避免 Recovery 依赖正在被恢复的 generation。Selector 格式必须极小、versioned，并保证 current 与 previous bootable BootstrapRuntime 都能解析。

Bootstrap Closure 是 replaceable ProductGeneration 之外的稳定、最小运行闭包。其职责只有：

```text
resolve InstallationId/InstanceId + PathProfile lifecycle roots
read/validate bootstrap metadata
select active/LKG ProductGeneration
resolve approved bootstrap/runtime generation
acquire bootstrap ownership
start/check private PostgreSQL
write BootstrapJournal
launch selected Host
enter bounded Recovery when normal boot cannot proceed
```

生产物理布局由 `PathProfile` 表达这一 ownership，而不是强制一个共同目录：

```text
ProgramRoot       → bootstrap/runtime/ProductGeneration code
InstanceRoot      → logical instance/binding metadata
ConfigurationRoot→ bootstrap/declarative configuration
DataRoot          → private PostgreSQL + owner durable data
BlobRoot          → CAS
RunRoot           → ephemeral run state
```

这些 root 可以共置，也可以分散到不同 OS path/volume。Bootstrap Closure 通过 logical root IDs 工作。

ProductGeneration update 不能覆盖当前正在执行的 Bootstrap Closure。Bootstrap/runtime 自身升级是独立 staged maintenance action：新 closure/runtime 必须预验证并保留上一个可启动 generation，随后原子切换 bootstrap metadata。

Bootstrap config 不能镜像 normal config，也不能依赖 normal ConfigurationService/SecretService。

### BootstrapJournal / Early Observability

PostgreSQL 尚不可用时必须仍能留下 bounded、crash-safe rescue projection：

```text
BootstrapActivityId
attempted bootstrap/runtime/ProductGeneration
boot stage + timestamps
private PG start result
last completed stage
Host launch/exit hint
safe/recovery override
LKG/candidate refs
```

它不是第二个 canonical database，也不承载正常业务 truth。Normal `ExecutionLineageService/EvidenceService` ready 后导入或引用本次 bootstrap chain。

Journal is per-BootId: `bootstrap-journal/<BootId>.json`（或等价固定格式）。每个 bootstrap/Host attempt 只 checkpoint 自己的 journal；并发失败启动不会覆盖 active Host 的 journal。`BootstrapStateStore` 可以在持 bootstrap ownership 时记录 last/active BootId ref，但 journal 内容本身不决定 active/LKG Authority。

### BootstrapStateStore

Bootstrap Closure 使用固定 `BootstrapStateStore` 保存 active/LKG bootstrap/runtime/ProductGeneration refs 与 bounded MaintenanceJournal pointer。它不是正常配置数据库。

状态格式必须是 versioned canonical JSON + digest + monotonic revision，并通过 `S15` 的 crash-safe atomic replace contract 提交。Recovery 启动时校验 current/previous state，拒绝 torn/corrupt metadata，不凭“文件存在”判断 active generation。

任何 bootstrap metadata mutation 都必须发生在 bootstrap ownership 下；同一 revision 只能有一个 committed winner。

## Bootstrap Lock → Host Lease Ownership Handoff

Pre-PostgreSQL window 使用 `@bybrave/proper-lockfile2` 5.0.0 behind bootstrap ownership adapter；private PostgreSQL ready 后使用 dedicated PostgreSQL session-level advisory Host lease。

必须形成无空窗 ownership chain：

```text
acquire bootstrap lock
→ resolve/start private PostgreSQL
→ acquire authoritative Host lease
→ ensure minimal HostOwnershipFence schema exists under bootstrap+lease ownership
→ publish new HostOwnershipToken
→ ONLY THEN:
   product/DBOS migration coordination
   first administrator claim state
   normal canonical writes
→ release bootstrap lock
```

Host lease证明：

```text
one active normal Host lease holder per instance
```

但 session advisory lease 本身不能阻止旧 Host 的其他 pooled connection 在 lease 丢失后继续提交。因此 normal ownership 还必须建立数据库级 `HostOwnershipFence`。

```text
Host obtains advisory lease
→ transaction locks HostOwnershipFence exclusively
→ publish new HostOwnershipToken + BootId
→ commit
→ canonical mutating transactions may begin
```

所有 canonical mutating transaction 必须：

```text
lock HostOwnershipFence in shared/read-compatible mode for transaction lifetime
→ verify current HostOwnershipToken == local token
→ perform mutation
→ commit
```

新 owner 切换 token 的 exclusive fence 必须等待旧 owner 已经进入的 mutating transactions 结束；token 切换完成后，旧 Host 的新 mutation 必然因 token mismatch 失败。Lease loss 到新 token 发布之间，旧 Host 由进程内 FENCED/admission stop 阻止新工作；若已经进入数据库 fence 的 transaction 仍完成，它在线性化顺序上属于旧 owner、且新 owner 必须等待它结束。`HostOwnershipToken` 是 fencing identity，不是 authentication secret。

首次 schema creation 在 ownership table 尚不存在时由 bootstrap lock + advisory lease 双重独占保护；建立 ownership schema 后必须发布首个 HostOwnershipToken，之后才释放 bootstrap ownership/进入 normal mutation。Restore 后同样发布新 token，绝不复用 snapshot 中的旧 token。

连接丢失意味着 ownership 不再被证明，应 fail-safe/quiesce。Pre-PG lock 只覆盖数据库 lease 尚不可取得的窗口；它不是第二个长期 Host authority。

Host lease 必须由 dedicated `HostLeaseConnection` 持有，不经普通 connection pool checkout/recycle。该 connection 只承担 session-level advisory ownership/health；任何 close/error/connection replacement 都视为 lease loss，触发 fencing/quiesce，而不是由 pool 自动换一条连接后继续假设 ownership 存在。


### Host Lease Loss Fence

Dedicated `HostLeaseConnection` 一旦 close/error/ownership validation failure：

```text
HostActualState → FENCED
stop new ingress/admission for consequential work
reject new System/Subject mutation commits through HostOwnershipFence
stop new Effect prepare/dispatch; every dispatch transition must verify HostOwnershipToken
abort/quiesce MicroSystem scopes cooperatively
preserve already-dispatching Effect as succeeded/failed/uncertain according existing proof
emit Bootstrap/Lineage failure record where possible
terminate normal Host runtime
```

旧 Host **不得**在原 runtime 中自动 reconnect → reacquire lease → resume。Lease loss 期间另一个进程可能已经成为 owner；重新进入 Normal Runtime 必须回到 Bootstrap Closure，从 bootstrap ownership + private-PG validation + Host lease acquisition 重新证明 ownership。

### Host Lease → Bootstrap Ownership Reverse Handoff

任何会停止/替换 private PostgreSQL、切换 bootstrap/runtime/ProductGeneration metadata，或进入 RecoveryOperation destructive window 的操作，都必须建立与 startup 对称的 ownership handoff：

```text
normal Host still holds PostgreSQL Host lease
→ acquire bootstrap ownership/lock
→ record MaintenanceJournal handoff
→ quiesce normal runtime / stop new mutating admissions
→ acquire HostOwnershipFence exclusively and revoke current HostOwnershipToken
   (waits all already-entered canonical mutating transactions)
→ release/lose Host lease only while bootstrap ownership is already held
→ stop/replace PostgreSQL or switch bootstrap state
→ recover/start target PostgreSQL
→ acquire target Host lease before normal runtime resumes
→ release bootstrap ownership
```

禁止：

```text
release Host lease
→ later try to acquire bootstrap lock
```

因为这会产生第二个 Host 获得 lease、随后又被旧进程停库/切 generation 的 race。

普通 Host 关闭 private PostgreSQL 时也遵守 reverse handoff。若 shutdown policy 选择保留 private PostgreSQL 运行，则不需要 stop-DB handoff，但 Host lease 仍必须在所有 product-owned runtime/effect quiesce 完成后才释放。

### PrivatePostgresProfile

最小 profile：loopback-only TCP、installation-owned persisted port、SCRAM、private data directory、cluster/bootstrap owner 与 migration/runtime/DBOS roles 分离。Normal Host 不以 cluster superuser 运行。Bootstrap credential 由 `BootstrapKeyProvider` 解锁，不能依赖 normal SecretService。

### PrivatePostgresController

Bootstrap Closure 通过极薄 `PrivatePostgresController` 使用产品固定的 PostgreSQL toolchain mechanics（`initdb` / `pg_ctl` / `postgres` / 必要 inspection tools），而不是自研数据库 process manager。

Controller 只拥有：

```text
initialize a new private cluster under bootstrap ownership
validate cluster metadata/version/identity
start/stop/restart private PostgreSQL
wait readiness with bounded timeout
select/validate the installation-owned loopback port
materialize least-privileged product roles during authorized bootstrap/migration
report structured Problem + Bootstrap Activity
```

首次 cluster creation 必须在空、受 installation-owner 权限保护的数据目录中完成，并原子记录：

```text
PostgreSQL major/profile version
private data-root identity
persisted loopback port
cluster identity/fingerprint when available
InstanceId / InstallationId association
initialization profile revision
```

正常启动使用 persisted port/profile。若端口被占用、`PG_VERSION`/cluster identity/profile 与 bootstrap metadata 不一致、数据目录处于未知状态：

```text
DO NOT silently init a new cluster
DO NOT silently connect to an arbitrary local PostgreSQL
DO NOT silently change durable identity
→ structured Problem
→ bounded repair/relocation/upgrade path or RECOVERY_REQUIRED
```

端口 relocation 只能在 bootstrap ownership 下作为显式 bootstrap mutation 提交，并通过 `BootstrapStateStore` 记录。PostgreSQL major upgrade 是 Product Update/migration operation，不由 normal start 自动执行。

Controller API 不暴露给 ordinary Extension/Subject/Operator Assistant；normal runtime只通过 PersistenceService/DBOS 等已授权 connection material访问数据库。

### Recovery Principal / Authentication

Normal administrator session 依赖 PostgreSQL，因此不能成为 Recovery 的唯一认证依赖。

Foundation 默认 `RecoveryPrincipal`：

```text
LOCAL_INSTALLATION_OWNER
```

证明边界是操作系统对 InstallationAnchor 与 bootstrap-relevant Instance/Configuration/Data roots 的本地访问控制：Recovery CLI 必须在目标机器上运行，并能通过受保护文件/目录/进程 ownership 检查；普通未授权 OS user 即使能执行 CLI binary，也不能读取/修改目标 instance recovery state。

约束：

```text
Recovery interface is local-only by default
no unauthenticated TCP/HTTP recovery endpoint
normal Host session cookie/token is not required
Recovery verbs are fixed and bounded
all successful/failed recovery attempts enter BootstrapJournal/Early Lineage
recovery identity never grants normal System/Subject Authority after Host resumes
```

平台可在该基线上增加 Windows token/ACL、Unix uid/gid/socket peer credential、sudo/admin elevation 或额外 recovery credential，但额外 credential 不能成为恢复 private PostgreSQL 所必需且又只存于该 PostgreSQL 的 circular dependency。

## Service Facade Boundary

跨 MicroSystem/Package ownership 的 Service dependency 不能把 provider raw implementation object 无包装泄露给 consumer。`ServiceRegistry` 解析后返回 Host-owned scoped facade/client：

```text
consumer ExecutionContext
+ required ServiceId/ContractVersionRange
→ resolved ProviderId/Generation
→ scoped Service facade
→ method invocation wrapper
→ child Activity / contract validation / permission scope
→ provider implementation
```

这不要求每次调用都做动态 service locator；Host 可以在 activation 时预绑定高性能 facade。关键是不允许跨 ownership boundary 绕过 Generation fence、Lineage 和 contract identity。

同一 MicroSystem 内部 helper/function 调用不需要强制包装成 Service invocation。

Service binding is activation-scope stable：required Service provider/generation 消失或发生 incompatible rebind 时，旧 facade 被 fence，dependent scope 进入 reconcile/dispose/restart，不在一次活跃 scope 中悄悄把 provider A 换成 B。

每次跨 ownership boundary 的 Service invocation 必须从 provider `ActivationResourceScope` 获取一个短生命周期 `InvocationLease`。Provider retirement 首先关闭新 invocation admission，再等待已有 lease 在 bounded drain window 内完成；超过窗口的调用收到 cooperative cancellation/fence，随后才能执行 provider finalizer/dispose。这样不会出现“调用仍在 provider 代码中运行，但 generation 已被逻辑销毁”的状态。`InvocationLease` 只保护正在执行的调用，不把 provider 变成全局引用计数容器，也不能替代 durable WorkItem。

Capability 可以按其 contract 由 Broker 在 invocation 时选择 eligible provider；每次选择都记录 ProviderId/Generation，并为实际 provider 取得相同的 invocation lease。若 capability 声明 sticky/explicit binding，则 provider change 也通过 ReconcilePlan 处理。

## Resource Ownership

每个 MicroSystem activation 必须有明确 `ActivationResourceScope`：

```text
sockets
timers
listeners
work handlers
service registrations
child process
temp files
```

无论底层 substrate 如何实现 finalizer/scope，都需要 Heptalogos ownership metadata 与 generation fence。

后台执行必须二选一：

```text
ephemeral task/timer/listener/process
→ ActivationResourceScope owns cancellation + await/finalizer + lineage

crash-surviving obligation
→ canonical WorkItem / Foundation durable primitive
```

Extension/MicroSystem 不得创建 unowned fire-and-forget Promise、长期裸 timer、不可追踪 child process。Foundation 可提供 `spawnScopedTask`/timer/process wrappers；exact mechanics 可由 runtime substrate/Node primitive承担。

不要重复实现库已经可靠提供的 finalizer/scope mechanics。

## Recovery Core 与 RecoveryOperation

固定能力：

```text
inspect BootstrapJournal/generation
inspect DB availability
safe mode
select LKG generation
stage/execute restore handoff
disable suspected optional generation for next boot
repair bounded bootstrap references
collect diagnostics
```

Recovery 不加载 Subject cognition、Operator AI 或 third-party runtime。

对会替换正常 durable substrate 的操作（restore、critical ProductGeneration/data switch、private PG repair、bootstrap metadata repair），使用 Bootstrap Closure 内的固定 `RecoveryOperation` + crash-safe `MaintenanceJournal`：

```text
operationId / ActivityId
fixed operation type
source/target refs
verified prerequisite refs
last completed stage
candidate/LKG refs
terminal outcome
```

它不是 generic workflow engine，也不能执行任意 shell/SQL。进入 destructive boundary 前由 normal Management path 负责 plan/auth/approval；进入后 RecoveryOperation 可以在 normal PostgreSQL/DBOS 暂时不可用时继续或安全判定下一步。

### First Administrator Claim

`FIRST_RUN_SETUP` 只允许 local one-shot claim ceremony：Bootstrap/Host 创建高熵 claim secret，保存在 installation-owner protected run/bootstrap location；CLI 通过 loopback claim endpoint + TTY/stdin password 原子创建首个 administrator。成功后 claim secret 删除/失效，未认证 claim endpoint 永久关闭。

不存在默认密码、argv/env password、远程未认证 claim、credential overwrite。初始 `SubjectDesiredState = STOPPED`。
