# S11 备份、更新、分发与平台

## 1. Backup Artifact

必须有 semantic manifest：

```text
backupFormatVersion
source ProductGeneration
contract/schema compatibility
participant snapshot set
Core PostgreSQL dump/snapshot
Configuration source/projection closure
Blob closure
encrypted secret/key material according policy
bootstrap refs
Extension generation refs + recovery-closure mode
data-lifecycle/purge-ledger revision
source ContinuityEpochId
hashes
```

不是任意 zip。

---

## 1.0 Instance Identity

Operational Backup manifest 必须记录 source `InstanceId / InstallationId`。Restore 默认语义是灾备继续原逻辑 instance：

```text
preserve InstanceId
create new InstallationId when target installation changes
create new BootId
create new BootstrapKeyProvider root on new installation
```

普通 Restore 不支持“无提示复制一个仍与源系统共享 InstanceId 的第二活跃实例”。真正 clone 必须是独立 high-risk `ClonePlan`，创建新 InstanceId，并显式处理 SecretRef、external account binding、Extension/Domain DataOwner stores 与 external side-effect identities。

## 1.1 Secret Closure

每个 SecretRef 在 backup manifest 中只记录允许暴露的 metadata 与 portability class：

```text
PORTABLE_ENCRYPTED
EXTERNAL_REFERENCE
REBIND_REQUIRED
NON_EXPORTABLE
```

`NON_EXPORTABLE` secret material 不进入 backup payload；`EXTERNAL_REFERENCE` 只恢复引用并重新验证 target availability；`REBIND_REQUIRED` 在 restore 后形成显式 blocked requirement；`PORTABLE_ENCRYPTED` 必须由独立 backup encryption trust domain 保护。

跨 installation restore 永不复制 BootstrapKeyProvider raw root/private PostgreSQL bootstrap credential；目标 installation 创建自己的 bootstrap root，再 rewrap/rebind允许迁移的 normal secrets。

### Recovery Closure Profile

Operational backup 必须声明 package/runtime closure 级别：

```text
RECOVERY_COMPLETE
  → 包含恢复该 snapshot 所需的 immutable Extension generations/native metadata/artifact closure（受许可/Secret policy约束）

REFERENTIAL
  → 只保存 verified source/provenance/digest refs；restore 依赖重新获得 exact artifact
```

默认面向灾备的 backup 应优先 `RECOVERY_COMPLETE`。`REFERENTIAL` backup 可以更小，但 Restore preflight 必须在 destructive stage 前证明所有 required generation 可取得且 digest/closure 一致；否则 BLOCKED，不能用“装个最新版 Extension”代替 snapshot generation。

ProductGeneration/runtime 是否嵌入 backup 可由 deployment/release policy决定，但 exact compatible generation 必须在 restore preflight 可验证取得。

## 2. Backup Participants / Live Backup

BackupCoordinator 以 logical DataOwner/BackupParticipant 枚举 required state：Core PostgreSQL、Configuration、Blob CAS、Secrets、Extension/Domain owner stores 与 recovery package closure。

Participant 可使用：

```text
TRANSACTIONAL_SNAPSHOT
NATIVE_ONLINE_SNAPSHOT
QUIESCE_AND_COPY
EXPORT_STREAM
IMMUTABLE_CLOSURE
REBUILDABLE
EXTERNAL_REFERENCE
```

允许 Subject 运行时 backup，但必须通过 `BackupEpoch` 与最小必要 barrier 证明 heterogeneous snapshot closure。需要更强 reproducibility 时可以 quiesce selected writers/Subject；不能把“停整个机器”或“所有数据都在 PostgreSQL”当唯一正确方案。

## 3. Data Lifecycle / Backup Fence

Backup 必须进入 retention/purge 语义：

```text

```

恢复历史 backup 不得静默复活已经 authoritative-purge 的数据。

## 4. Restore Safety

Restore 是会替换 normal durable substrate 的 maintenance/recovery operation。

进入 destructive stage 前：

```text
normal SystemAction plan/auth/approval
→ verified artifact + compatibility + backup prerequisites
→ maintenance handoff
```

进入后使用 Bootstrap Closure 的 fixed `RecoveryOperation/MaintenanceJournal`，而不是只依赖正在被替换数据库中的 DBOS workflow。Journal 只记录固定操作类型、ActivityId、refs、last-completed stage、candidate/LKG 与 terminal outcome。

Restore staged smoke 必须 effects-disabled；失败必须能从 journal 判断继续、回退或 `RECOVERY_REQUIRED`。

### Restore Continuity Epoch

Destructive restore 是一次本地时间线 discontinuity。Bootstrap Closure 在切入 restored canonical store 之前创建新的 `ContinuityEpochId`，写入 BootstrapState/MaintenanceJournal，并在 restored DB 的正常 Host ownership 建立前 materialize 为当前 epoch。

```text
InstanceId      remains the logical instance
InstallationId changes only when physical installation changes
BootId          changes every boot
ContinuityEpochId changes on destructive state restore/rollback
```

新 epoch 触发固定 reconciliation。**这些数据库变更必须在 restored DB 上、normal DBOS launch/queue recovery/Management exposure 之前完成**，避免 snapshot 中旧 workflow/session 先恢复执行。此时由 Bootstrap-owned fixed RecoveryOperation 执行白名单式 offline recovery mutation；normal HostOwnershipToken 尚未开放，普通 repository/Extension 不可运行：

```text
rotate/increment authEpoch and invalidate all restored normal sessions
apply explicit `administratorCredentialRestorePolicy` from the RestorePlan; restoring a snapshot can roll credential verifiers back in time and this MUST NOT be hidden
pending approvals → superseded by restore
restored/in-flight ManagementOperations → interrupted unless the fixed RecoveryOperation owns them
non-terminal consequential WorkItems → WAITING_RESTORE_RECONCILIATION
non-terminal EffectOperations that could have dispatched after snapshot → uncertain/reconcile; never auto-resend
revalidate SecretRef/trust/package generation closure
reconcile purge ledger and external integration cursors
```

Pure/read-only/derived work 只有在其 contract 明确声明 restore-safe 且 payload/version/preconditions 仍有效时可以自动继续。

原因是 backup 之后外部 IM、API、tool 或人类审批可能已经发生；恢复旧 DataOwner snapshot set（包括 Core PostgreSQL）不能证明这些外部事实被回滚。

跨 installation restore 还必须使用 target installation 的 bootstrap/TUF installation trust state；不得用 snapshot 回滚 InstallationAnchor/BootstrapKeyProvider/TUF anti-rollback state。Instance-level Extension trust/config 若来自 snapshot，必须进入 restore security revalidation。

### Administrator Credential Restore Policy

Destructive restore can revive an older password verifier even though all sessions are invalidated. `RestorePlan` therefore records one of:

```text
PRESERVE_SNAPSHOT_VERIFIERS
LOCAL_RESET_REQUIRED
```

`PRESERVE_SNAPSHOT_VERIFIERS` is allowed only when the operator explicitly accepts verifier rollback as part of restoring that snapshot; the resulting ContinuityEpoch still invalidates all sessions/approvals and requires fresh authentication.

Cross-installation restore defaults to `LOCAL_RESET_REQUIRED`: before remote Management exposure, a local installation owner uses the bounded recovery/bootstrap path to set a new administrator verifier. The password is never passed via argv/environment. Disaster recovery that cannot preserve an existing verifier remains operable through the local installation-owner recovery boundary.

The chosen policy, source backup identity, target InstallationId and resulting authEpoch are durable Audit/Evidence and Lineage facts.

## 7. Candidate Acceptance 与 Migration Fence

ReleaseManifest 在 mutation 前声明：

```text
ProductGeneration compatibility
DBOS durable-code compatibility
DB migration class:
  BACKWARD_COMPATIBLE
  RESTORE_REQUIRED
  NO_ROLLBACK
```

`BACKWARD_COMPATIBLE` 必须声明旧 LKG 可接受的 schema range。`RESTORE_REQUIRED` 必须在 migration 前验证 recoverable backup/snapshot。`NO_ROLLBACK` 进入高风险显式 plan，不能假装有安全 down migration。

Candidate acceptance：

```text
stage generation
→ static/native/schema compatibility
→ prepare required recovery artifact
→ maintenance
→ migrate according declared class
→ candidate boot in no-effect acceptance profile
→ readiness/conformance
→ activate
```

失败严格执行预声明 rollback strategy。

### Durable-code version

`ProductGeneration`、DBOS `applicationVersion/durable-code version`、Extension `PackageGeneration` 是三个独立轴。Extension install/upgrade 不改变 DBOS applicationVersion。

真正不兼容的 DBOS durable workflow code 默认在旧 workflow drain 前阻止 ProductGeneration 切换；若未来需要 legacy worker，必须是 bounded durable worker 且不持 normal Host/System Authority lease。

## 8. Product Layout 与 Bootstrap Closure

生产布局必须通过 `PathProfile` 区分 replaceable Program/Package generation 与 persistent Instance/Configuration/Data/Secret/Blob roots；不要求存在共同父目录：

```text
ProgramRoot       → bootstrap/runtime/ProductGenerations
InstanceRoot      → logical instance/extension-instance metadata
ConfigurationRoot→ bootstrap/declarative/owner-native config
DataRoot          → Core PostgreSQL + owner durable stores
BlobRoot          → CAS
BackupRoot        → backup artifacts
RunRoot           → ephemeral run state
```

Bootstrap Closure 只负责 generation selection/verification、bootstrap ownership、PathProfile/bootstrap locator、private PG bring-up、RecoveryOperation 和 Host launch。ProductGeneration update 不覆盖当前执行 bootstrap closure，也不隐式删除 Config/Data/Secret。

Bootstrap/runtime 自身升级作为独立 staged maintenance：验证新 generation → 保留 previous bootable closure/runtime → 原子切换 bootstrap metadata → 启动验证；失败可选择 previous closure/runtime。

Normal CLI/Host 使用 loopback Management HTTP；Recovery CLI 通过 bounded bootstrap/recovery verbs，不提供 root shell。

### Bootstrap Metadata Commit

active/previous/LKG bootstrap/runtime/ProductGeneration refs 通过 `BootstrapStateStore` 的 versioned canonical state + digest + revision 提交，并使用 `S15` 定义的 crash-safe atomic replace protocol。Update/rollback 不能只改一个裸 symlink/path/text file 就宣称切换成功。
