# 开发阶段闭包：稳定化与兼容性治理

**性质：** 当前态架构治理规则。它定义 milestone 完成后的稳定化和候选闭环，不把未来 review、CI 或 merge 结果预写成已经通过。

## 1. 功能完成不等于阶段闭包

```text
Hn functional completion != Hn closure
Hn-S is mandatory before Hn CLOSED
Hn-S is short/bounded, not a second development stage
```

功能 milestone 证明目标行为已实现；`Hn-S` 还必须清除会让下一阶段依赖不可信的 canonical-state、Authority、recovery、边界和当前证据缺陷。稳定化不得借机实现下一阶段功能、引入新 subsystem，或把 bounded corrective work 扩展为第二轮开发。

## 2. A/B/C scope budget 与 Stop Rule

每个 Hn-S 按以下预算分类：

```text
A — closure blockers: MUST fix
B — bounded structural debt: 只做 local, non-expanding edits
C — explicitly out of scope: defer
```

任何发现若需要新 subsystem、major architecture expansion 或 substantial new capability work，必须记录为 C 或待重新授权的架构问题。只有当 H1 无法在不处理它的情况下诚实关闭时，才能重新提交 scope decision；稳定化实现不可用审美重构替代该判断。

## 3. Hn-S 执行与最终候选

稳定化默认使用一个 bounded stabilization plan、一个短生命周期分支和一个 Draft PR：

```text
one bounded plan / one branch / one PR / final external closure tuple
```

只有在确实需要串行独立阶段时，才升级为 control record + phased plans；此时只有 control record 指定的 `governingPlan` 可以执行。普通 stabilization commit 不 dispatch CI。所有 repository mutation 必须在 final independent review 之前完成，之后再有 commit 就会使候选失效。

最终授权绑定完整候选对：

```text
ReviewCandidate = (base_sha, head_sha)
```

候选闭包要求实现计划完成、本地 qualification 完成、独立审查对 exact `(base_sha, head_sha)` 为 PASS、Ubuntu/macOS/Windows 手动 final CI 对同一候选对为 PASS，并在 squash merge 前确认 base/head 仍未变化。review、CI 和 merge evidence 是外部 candidate-governance evidence；合并后的 repository truth 只能由 separate docs/evidence-only PR 在 closure tuple 实际发生后按证据 reconciliation，不能由 behavior candidate 的 post-review commit 自行伪造或补录。

合并后的 behavior candidate 不可变。post-merge truth reconciliation PR：

```text
- 不得修改 production code、tests 或 behavior contract
- 必须引用外部观察到的 review/CI/merge evidence
- 必须运行 repository/corpus/document gates
- 只在 closure tuple 实际发生后把 Hn OPEN 改为 CLOSED
- 不得重跑或改写已经合并的 behavior candidate
```

对 H1：squash merge 成功先构成 H1 semantic closure event；reconciliation PR
记录 `H1: CLOSED / H2: ELIGIBLE`，且该 PR 合并前 H2 不得开始执行。

## 4. 当前 H1 状态与 H2 门禁

当前状态为：

```yaml
M5B: CLOSED
H1_FUNCTIONAL: COMPLETE
H1_STABILIZATION: ACTIVE
H1: OPEN
H2: NOT_ELIGIBLE
```

H1 只有在 H1-S 候选完成全部外部闭包 tuple 并成功 squash merge 后才关闭。H2 不能在 H1-S squash merge 之前开始；不得把计划状态、当前代码、历史 qualification 或预期 CI 结果描述为已经满足未来闭包。

## 5. PRE_PRODUCTION 兼容性边界

```text
VERSIONED != HISTORICALLY COMPATIBLE.
COMPATIBILITY REQUIRES A DECLARED OBLIGATION.
CompatibilityEpoch = PRE_PRODUCTION.
```

durable payload 仍必须有显式 `schemaVersion`/contract version；但在 `PRE_PRODUCTION` 下，merged commit、内部 retained developer DB、local fixture、previous dev build 和其他项目-owned development history 都不会产生兼容义务。当前 shape 变化直接重写 canonical V1，obsolete development shape 必须 reset/reject；不得仅为历史新增 V2/V3、legacy reader、upcaster、bridge migration、alias、shim 或 dual format。首次 production compatibility 之前，migration history 也是可重写的 development material，应 squash/rewrite current baseline 并重建 dev/test state。只有真实 retained state 或明确 external consumer 才能要求兼容路径；进入 production compatibility epoch 必须经过显式 architecture decision。

历史实现和 qualification 记录可以作为 `Historical Evidence` 保留；它们不等于 `Current Evidence`，也不能重新获得当前 Authority。当前 property ledger 必须只描述实际存在且已用 claim-matched evidence 验证的行为。
