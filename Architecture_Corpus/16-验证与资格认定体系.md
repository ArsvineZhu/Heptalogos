# 验证与资格认定体系

## 1. 五类不同证据

```text
Dependency Selection Evidence
Code Correctness
System Semantic Correctness
Product Qualification
Research Evaluation
```

它们不能互相替代。

尤其：

```text
选择一个 generic dependency
!=
证明最终 shipping product
```

---

## 2. Dependency Selection Evidence

依赖选择按最小充分证据逐级升级：

### L0 — Direct Evidence

优先使用：

```text
official specifications/docs
API/types/source
upstream tests
release/changelog
package metadata/dependency tree
license/support matrix
maintenance history
```

如果关键问题已经能从可靠证据确定，不写 spike。

### L1 — Micro Probe

只验证一个无法由 L0 决定的性质。

典型规模：

```text
synthetic services
fake transport
local test server
minimal schema
small process fixture
```

不得依赖真实 Subject、Milky、Memory、完整 Extension Package Manager 或其他产品系统，除非那个产品语义本身就是待验证边界。

### L2 — Boundary Probe

只有候选基本机制成立，但 adapter/ownership mapping 仍不明确时才使用。

比较：

```text
thin candidate adapter
vs
explicit/native baseline
```

重点测 adapter complexity、double lifecycle、diagnostics、framework leakage。

### Architecture Selection

L0-L2 足以决定角色后，更新：

```text
RoleDecision
```

不要求先完成最终跨平台产品实现。

当前 Foundation provider selection 已关闭；本 Corpus 不再要求额外 pre-implementation Pilot 才能进入 Implementation Plan。后续 Q/C evidence 仅用于 adopted-route conformance 或真实 product qualification。

当前验证路线**不依赖 GitHub Actions**。GitHub Actions 可以保持关闭；任何 Foundation selection、Implementation Plan gate 或本地验收都必须能够通过仓库内可直接执行的命令与证据产物完成。未来若启用 CI，它只是这些本地可复现 gate 的自动化投影，不得成为唯一 Authority。

---

## 2.1 Framework Leakage Gate

Repository/CI 必须静态验证稳定边界没有被具体 mechanics/framework 类型污染：

- architecture/domain/public Extension contracts 不 import Fastify、DBOS、Cordis、Kysely/pg、Pino/OpenTelemetry、Cedar engine 或 package-filesystem implementation types；
- Extension SDK 不依赖 Host internals；
- CLI 不直接 import repositories、DBOS、PrivatePostgresController 或 RuntimeSupervisor internals；
- Service/Capability ports 使用 Heptalogos-owned semantic types；
- adapter/mechanics dependencies 不反向污染 stable contracts。

推荐使用 TypeScript project references、Nx tags/module-boundary rules、ESLint import constraints 或等价机制。该 Gate 验证依赖方向，不要求每个逻辑模块成为独立 workspace package。

---


## 2.2 Toolchain Conformance Gate

Repository canonical compile/type compatibility must prove the adopted toolchain rather than a legacy fallback:

```text
TypeScript 7 canonical tsc/typecheck
ESNext / NodeNext / ESM-first
skipLibCheck=false for compatibility evidence
@types/node major matches shipping Node major
TS6 compiler API lane is isolated to tools that require it
```

Representative adopted dependencies must be imported/compiled under TS7. A library's upstream dev compiler version alone is not a compatibility blocker; distinguish hard peer/runtime constraints from consumer `.d.ts` compatibility and upstream build-tool choices.

Exact version selection must refresh registry/upstream evidence at Catalog freeze/upgrade. Prerelease labels do not replace maturity/risk qualification.

Detailed plan: `qualification/DEPENDENCY-QUALIFICATION.md` → `C-TOOLCHAIN-01`.

## 6. Real PostgreSQL

涉及：

```text
transaction
constraints
advisory lock when used
LISTEN/NOTIFY
DBOS datasource
migration
```

必须使用 real PostgreSQL。

Testcontainers 是开发/CI mechanics；不证明 shipping private PostgreSQL 跨平台可用。

### HostOwnershipFence concurrency

使用真实 PostgreSQL 做确定性多连接/多进程测试：

```text
Host A holds advisory lease + token A
A1/A2 concurrent mutating transactions hold shared fence
Host A loses/relinquishes lease
Host B obtains lease
B exclusive fence waits A1/A2
B publishes token B
new/stale A mutation with token A fails
B mutation succeeds
```

还必须验证 graceful reverse handoff、lease connection kill、restore offline recovery window 与 token re-publication。该测试证明 single-Host mutation fencing，而不是仅证明 advisory lock API 可调用。

---

## 7. SignalService Conformance

PostgreSQL `LISTEN/NOTIFY` 作为 SignalService mechanics 必须验证：

```text
listener connection kill/reconnect
re-LISTEN after reconnect
lost notification + canonical re-query
notification storm/coalescing
payload contains no unique durable truth
dedicated connection ownership
```

丢 Signal 只允许增加 latency，不允许丢失 canonical work/state。

## 8. Crash Matrix

至少在以下 Authority 边界 kill process：

```text
MessageFact/WorkItem authoritative commit 后 dispatch 前
Reaction result 后 Review/DecisionCommit 前
DecisionCommit 后 Action execution 前
Effect dispatching commit 后 external call 前
external response 后 terminal commit 前
approval wait
config activation
Extension generation switch
backup/update/restore switch
```

重启真实 Host 验证 canonical recovery。

## 22. Source-less / Native Qualification

在仓库外验证 exact release artifact。

任何 direct/transitive native/WASM binary 都属于产品闭包。

如果 artifact digest 或 native dependency closure 改变：

```text
affected product qualification → NOT_RUN
```

不得 acceptance 后 rebuild 再沿用旧证据。

---

## 23. Advanced Research Evaluation

高级 cognition subsystem 的算法评估**不属于 Foundation release gate**。

对应 subsystem 开始研究时，必须单独建立：

```text
Hypothesis
Baseline
Intervention
Dataset/Episodes
Metrics
Ablation
Failure modes
```

Foundation 只保证其 hooks/contracts 能被 contract/conformance tests 验证。

---

## 24. Gate Truthfulness

结果只有：

```text
PASS
FAIL
NOT_RUN
BLOCKED
```

文档声称、analogous test、单一 OS、mock success 或“理论上支持”都不能自动变成 PASS。

---

## 25. Configuration Governance Qualification

必须有静态/动态检查：

```text
behavior-affecting literals classified
ConfigurationDefinitions schema-valid
defaults/active revisions valid
runtime consumers exist
save != activate
activation impact matches metadata
platform applicability correct
SecretRef never plaintext
removed/renamed definitions have migration
Management Contract projection complete
CLI reference coverage complete
```

Configuration scanner 的目标是强制分类，不是机械消灭所有 literal。
